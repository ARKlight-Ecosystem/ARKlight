# v0.060 -- User-defined, reusable components

A plain Python render function can now become a real, named component
type the compiler itself understands -- not just an invisible-to-the-
compiler Python function call. `component(...)` gives it a checked
props contract, participation in `arklight search`'s typo suggestions,
optional default styling, and (experimentally) per-backend rendering
and its own instance-scoped reactive state.

Landed as 5 staged sub-releases (`v0.060-stage0` through Stage 4),
rolled up here into one milestone-level summary -- see `PROGRESS.md`'s
Snapshot table for the individual per-stage record.

## What shipped

- **Registration + props contract** -- `component(props=...)`/`Prop`;
  an unknown or missing-required prop fails the build with a clear
  message, not a raw Python `TypeError` (Stage 0).
- **Macro expansion (Option A, the default)** -- a component call
  expands into its built-in subtree before Validation ever runs, so
  every existing compiler stage keeps working unchanged (Stage 0).
- **Typo diagnostics** -- a mistyped call to a registered component
  now gets the same "did you mean...?" treatment a built-in typo
  already does (Stage 1).
- **Default styling** -- `component(default_style={...})` folds rules
  into the site's stylesheet under a `.ComponentName` class, applied
  automatically to call sites that use it (Stage 2).
- **Per-backend rendering (Option B, experimental)** --
  `component(mode="registry")` plus `.register_backend(name)` lets a
  component render differently per backend, falling back to its
  shared render function where no override exists (Stage 3).
- **Component-owned state** -- `component(state={...})` gives a
  component its own local, instance-scoped `State(...)`-equivalent;
  every call site gets an independent copy (Stage 4).
