# v0.060, Stage 0 -- User-defined, reusable components (registration + Option A macro expansion)

The first stage of `v0.060` (milestone still IN PROGRESS overall): a
plain Python function can now become a real, named component the
compiler itself understands, instead of just an invisible-to-the-
compiler Python function call.

## What shipped

- `component(*, props=None, mode="macro")` -- decorate a render
  function and it becomes callable exactly like a built-in:

  ```python
  @component(props={"active": Prop(default=None)})
  def NavBar(active=None):
      return Container(
          Link("Home", href="/"),
          Link("About", href="/about"),
      )

  NavBar(active="home")
  ```

  A call site's props are checked against the declared contract -- a
  missing required prop, an unknown prop, or a type mismatch fails the
  build with a clear message, not a raw Python `TypeError`.
- **Option A (macro expansion, the default)** -- a component call is
  fully expanded into its underlying built-in subtree before the
  compiler's Validation stage ever runs, so every existing rule (schema
  checks, required props, text-only containment, ...) applies to a
  user component's output automatically, with zero changes needed
  anywhere downstream.
- **Option B (registry-based, EXPERIMENTAL)** -- `mode="registry"` is
  now selectable for a project that will eventually want per-backend
  rendering identity. It's not yet a different outcome (see the
  implementation doc below) -- picking it today records the intent for
  a later stage to build on, without changing what happens at build
  time yet.
