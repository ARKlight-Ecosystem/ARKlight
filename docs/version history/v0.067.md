## JS vocabulary, stage 7 of 10: the list-scalar derivations catalog (SHIPPED)

Seventh rung -- reduces a list-typed `State` value to a scalar the
way `sum`/`count` already reduce multiple *named* states. Still
scalar-out, so it fits today's `DERIVATION_REGISTRY` as-is; the
list-in/list-out sort/filter registry these read like siblings of
stays out of scope for this ladder (Tier 3, still an open proposal).
Nine new `Derive.*` kinds; each is a registry entry, a JS fragment and a
build-time Python mirror, no new IR node.

### What shipped

| Kind | Python call | Result |
| --- | --- | --- |
| `list_length` | `Derive.list_length("items")` | item count, `0` for a non-list |
| `list_min` | `Derive.list_min("scores")` | smallest item read as a number; `Infinity` if empty |
| `list_max` | `Derive.list_max("scores")` | largest item read as a number; `-Infinity` if empty |
| `list_average` | `Derive.list_average("scores")` | mean of items read as numbers; `NaN` if empty |
| `list_first` | `Derive.list_first("items")` | first item as-is, `None`/`null` if empty |
| `list_last` | `Derive.list_last("items")` | last item as-is, `None`/`null` if empty |
| `list_includes` | `Derive.list_includes("tags", "x")` | `True` if any item `=== "x"` |
| `list_any` | `Derive.list_any("scores", "gt", 90)` | `True` if some item satisfies `item > 90` |
| `list_all` | `Derive.list_all("scores", "gte", 70)` | `True` if every item satisfies `item >= 70` |

- **A value that isn't a list reads as an empty list.** `Array.isArray`
  is the client-side test, so a string, a number, an object, `None`, and
  a name never given a value all behave like `[]`. `list_length` is
  list-only, unlike `Derive.count`, which also measures a string or an
  object.
- **Numeric kinds read each element like the math catalog reads a state
  value** -- `Number(x) || 0` (`NaN` and `-0` become `+0`) -- narrowed to
  numbers, strings and booleans; `None`, a nested list and an object
  read as `0`.
- **`list_includes`/`list_any`/`list_all` return a boolean**, so any of
  the three can drive `Show(Predicate.truthy(...))` directly.
  `list_any`/`list_all` take one of the existing six `compare` operators
  plus a literal -- never a callback, validated at build time the same
  way `Derive.compare` is. `eq`/`ne` compare the element itself against
  any literal scalar; the four relational operators compare the element
  read as a number against a numeric literal. An empty list makes
  `list_any` `False` and `list_all` vacuously `True`, matching
  `[].some(...)`/`[].every(...)`.
- **Same verdict server-side and client-side.** `arklight/ir/js_list.py`
  (new) is the build-time mirror -- same role as `js_numeric.py`/
  `js_string.py`/`js_predicate.py` -- reproducing `Number(string)`'s own
  grammar (radix literals, `Infinity`, JS whitespace) and `===` equality,
  never Python's looser `float()` or `1 == True`. Confirmed with a
  roughly 15,000-case Node parity sweep.
- **`Bind(...)`'s pre-filled HTML now spells a missing value `null`**,
  not Python's `None` -- needed so `list_first`/`list_last` of an empty
  list pre-render the way the client would write it back.
- **No fragment spreads a list into a call or needs a post-2022
  browser:** loops and indexing throughout, not `Math.min(...list)`
  (which throws past roughly 100k items) or `.at()`; checked against a
  500,000-item list in Node.

### Not in this stage

- **No list-in/list-out registry entry** (map/filter/sort over a list).
  That stays Tier 3 of the wider proposal, an open design question about
  a different registry shape, not a gap in this ladder.
- `Derive.list_includes`'s literal, and `list_any`/`list_all`'s, are
  restricted to JSON scalars (str/bool/`None`/finite number, an integer
  within `+/-2**53`) -- the same bound `Predicate.one_of(...)`'s values
  already carry, shared through one validator function.

## `Provider`, stage 3 of 6: JS backend emission (SHIPPED)

Emits the fixed, minimal config a validated `Provider` declaration
needs at runtime -- no network call, no vendor SDK, no generated glue
that actually talks to anything.

### What shipped

- **`window.ARKLIGHT_PROVIDER`** in `arklight.js`
  (`arklight/backend/js/render.py`'s `_provider_config_js`):

  ```js
  window.ARKLIGHT_PROVIDER = Object.freeze({
    name: "firebase",
    capabilities: Object.freeze(["auth", "read"])
  });
  ```

  Read-only, for the site author's own script to read -- the same
  all-caps-window-global convention as `window.ARKLIGHT_ON_ERROR`, in
  the other direction. Site-wide: one provider per `Site`.
- **Zero output when unused.** A site with no `Provider` gets no extra
  byte; one with a Provider still differs from one without in only
  `arklight.js` and `sbom.txt` -- pages and stylesheet are unchanged.
  The object is emitted whether or not the devtools console reminder is
  enabled.
- Names are written as escaped string literals, so quotes,
  `</script>`, line-separator characters and non-ASCII round-trip
  exactly.
- Stale "adds no markup, config or script" wording in
  `arklight/provider.py`, `Provider`'s docstring and the
  `provider-integration` notice was corrected.

### Not in this stage

- **DOM hooks and `State(...)` keys.** The proposal's section 3 says the
  blob describes what capabilities are "wired to". There is no
  authoring surface for wiring a capability yet, so the object holds
  only `name` and `capabilities`; fields can be added later without
  breaking readers.
- Per the later previews: the external `<script src>` prop (stage 4),
  `arklight search` integration (stage 5), the final capability enum
  (stage 6). No CSP change, no concrete provider. The `.arklight` binary
  still doesn't round-trip `provider`, so a build from a decoded file
  emits no object.
