## JS vocabulary, stage 7 of 10

Seventh rung -- reduces a list-typed `State` value to a scalar the
way `sum`/`count` already reduce multiple *named* states. Still
scalar-out, so it fits today's `DERIVATION_REGISTRY` as-is; the
list-in/list-out sort/filter registry these read like siblings of
stays out of scope for this ladder (Tier 3, still an open proposal).

### What's planned

- `list_length`, `list_min`, `list_max`, `list_average`,
  `list_first`, `list_last`, `list_includes`, `list_any`, `list_all`

## `Provider`, stage 3 of 6: JS backend emission (SHIPPED)

Emits the fixed, minimal config a validated `Provider` declaration
needs at runtime -- no network call, no vendor SDK, no generated glue
that actually talks to anything.

### What shipped

- **`window.ARKLIGHT_PROVIDER`** in `arklight.js`
  (`arklight/backend/js/render.py`'s `_provider_config_js`):

  ```js
  window.ARKLIGHT_PROVIDER = Object.freeze({
    name: "firebase",
    capabilities: Object.freeze(["auth", "read"])
  });
  ```

  Read-only, for the site author's own script to read -- the same
  all-caps-window-global convention as `window.ARKLIGHT_ON_ERROR`, in
  the other direction. Site-wide: one provider per `Site`.
- **Zero output when unused.** A site with no `Provider` gets no extra
  byte; one with a Provider still differs from one without in only
  `arklight.js` and `sbom.txt` -- pages and stylesheet are unchanged.
  The object is emitted whether or not the devtools console reminder is
  enabled.
- Names are written as escaped string literals, so quotes,
  `</script>`, line-separator characters and non-ASCII round-trip
  exactly.
- Stale "adds no markup, config or script" wording in
  `arklight/provider.py`, `Provider`'s docstring and the
  `provider-integration` notice was corrected.

### Not in this stage

- **DOM hooks and `State(...)` keys.** The proposal's section 3 says the
  blob describes what capabilities are "wired to". There is no
  authoring surface for wiring a capability yet, so the object holds
  only `name` and `capabilities`; fields can be added later without
  breaking readers.
- Per the later previews: the external `<script src>` prop (stage 4),
  `arklight search` integration (stage 5), the final capability enum
  (stage 6). No CSP change, no concrete provider. The `.arklight` binary
  still doesn't round-trip `provider`, so a build from a decoded file
  emits no object.
