## JS vocabulary, stage 8 of 10

Eighth rung -- the first stage past JS's own built-ins: numeric
operations Python/Rust/C++ standard libraries offer that JS's `Math`
has no equivalent for at all.

### What's planned

- `lerp` (C++20 `std::lerp`) -- linear interpolation, common in
  progress-bar/slider/drag-to-scale UI, hand-rolled everywhere today
  because JS has no built-in.
- `midpoint` (C++20 `std::midpoint`) -- overflow-safe average.
- `saturating_add`/`saturating_subtract` (Rust
  `saturating_add`/`saturating_sub`) -- clamps to a fixed min/max
  instead of over/underflowing, complements `clamp` (`v0.064`) but
  reads more naturally for increment/decrement-style UI.
- `value_or` (Rust `Option::unwrap_or`) -- a named state value, or a
  fallback if it's `null`/`undefined`/empty.
- `first_present` (Rust `Option::or` chains / SQL `COALESCE`) --
  first non-empty value across 2+ named states, in order.

## `Provider`, stage 4 of 6: external script loading

Resolves the proposal's own open question (§7.1): a `Provider`
declaration alone doesn't get a real vendor SDK (e.g. the actual
Firebase JS SDK) loaded into the page. This stage adds the small,
separately-gated primitive that makes the contract usable end-to-end.

### What's planned

- An authored, experimental way to add an external `<script src>` to
  a page's `<head>` (e.g. a gated `Page(scripts=[...])`), closest
  existing precedent being `css-import`'s `@import` and its "fetched
  at request time, can't be validated by ARKlight" experimental note.
