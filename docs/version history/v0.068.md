## JS vocabulary, stage 8 of 10 (SHIPPED)

Eighth rung -- the first stage past JS's own built-ins: numeric
operations Python/Rust/C++ standard libraries offer that JS's `Math`
has no equivalent for at all. Every kind is a pure registry-fragment
addition (`arklight/backend/js/derivations/lerp.py` etc.), same shape
as every earlier rung -- no new IR node, no parser, nothing that
touches `eval`/`new Function`.

### What shipped

- `Derive.lerp(a, b, t)` (C++20 `std::lerp`) -- linear interpolation,
  `a + t * (b - a)`, with `t == 0` returning exactly `a` and `t == 1`
  returning exactly `b`. Common in progress-bar/slider/drag-to-scale
  UI, hand-rolled everywhere today because JS has no built-in. Reads
  three names, in order.
- `Derive.midpoint(a, b)` (C++20 `std::midpoint`) -- `a + (b - a) / 2`,
  overflow-safe average of two values. Reads two names.
- `Derive.saturating_add(a, b, min=, max=)` / `Derive.saturating_subtract(a,
  b, min=, max=)` (Rust `saturating_add`/`saturating_sub`) -- the
  sum/difference of two named values, clamped to a fixed literal
  `[min, max]` instead of running past it (`min` above `max` is a build
  error). Complements `clamp` (`v0.064`) but reads more naturally for
  increment/decrement-style UI, e.g. a quantity stepper that should stop
  at a ceiling or at zero rather than keep going.
- `Derive.value_or(name, fallback)` (Rust `Option::unwrap_or`) -- the
  named value, or a literal `fallback` if it's
  `null`/`undefined`/an empty string.
- `Derive.first_present(*names)` (Rust `Option::or` chains / SQL
  `COALESCE`) -- the first of two or more named values that isn't
  `null`/`undefined`/an empty string, in order; if every one is empty,
  returns the last name's (still-empty) value.

`arklight/ir/js_numeric.py` gained `js_lerp`/`js_midpoint`, the
Python-side mirrors of the two arithmetic edge cases (`lerp`'s `t == 0`/
`t == 1` special cases, `midpoint`'s overflow-safe formula), so a
page's server-rendered `Bind(...)` text never disagrees with what the
client recomputes -- the same "build-time mirror" discipline every
earlier stage in this ladder follows. `tests/test_js_vocabulary_v0068.py`
added.

## `Provider`, stage 4 of 6: external script loading (SHIPPED, `0.06613`)

Resolves the proposal's own open question (§7.1): a `Provider`
declaration alone doesn't get a real vendor SDK (e.g. the actual
Firebase JS SDK) loaded into the page. This stage adds the small,
separately-gated primitive that makes the contract usable end-to-end.

### What shipped

- `Page(scripts=[{"src": "https://example.com/sdk.js", ...}])` -- an
  authored way to add an external `<script src>` to a page's `<head>`,
  the same `{attribute: value}`-dict shape `Page(links=[...])` already
  uses. Validated in `arklight.ir.validate._validate_page_head_extensions`:
  a non-empty list of non-empty attribute dicts, each requiring a `src`
  (an entry with nothing to load isn't meaningful) and rejecting a
  `"javascript:"` `src` outright (that's inline code, not an external
  file, and this primitive isn't an inline-execution escape hatch).
  Rendered verbatim -- no asset-path resolution, same reasoning `links`
  already documents -- at the end of `<head>`, after every other
  extension point, by `arklight/backend/html/head_meta.py`.
- Gated as its own `provider-scripts` experimental feature
  (`arklight/experimental.py`), independent of `provider-integration`:
  a page can declare a `Provider` with no script, or load a script with
  no declared `Provider`, and each is warned about on its own. Closest
  existing precedent is `css-import`'s `@import` and its "fetched at
  request time, can't be validated by ARKlight" note -- `provider-scripts`
  carries the same disclaimer, plus a reminder that the script also has
  to clear the page's own `script-src` CSP default
  (`Site(trusted_script_origins=[...])`, `arklight/backend/html/csp.py`)
  to actually load.
- `arklight/ir/build.py` records one `ExperimentalUsage` per
  `Page(scripts=[...])`, folded into the same `WebsiteIR.experimental_usages`
  list every other gated feature already reports through
  (`arklight/backend/js/render.py`'s devtools console reminder,
  `sbom.txt`).
- `tests/test_provider.py`/`tests/test_html_head_meta.py` extended:
  validation errors (missing `src`, `javascript:` `src`, non-string
  attribute values), the independent gating of `provider-scripts` from
  `provider-integration`, and an end-to-end build asserting the
  `<script>` tag actually lands in the rendered page.

Out of scope, unchanged from the proposal: no bundled vendor SDK ships
with ARKlight, and the referenced script's own contents remain
entirely outside anything ARKlight validates -- this stage only adds
the authored way to *point at* one.
