# v0.062 -- JS vocabulary: string casing + comparison predicates

Second rung of the JS vocabulary expansion (see
[`docs/Proposals/JS-VOCABULARY-EXPANSION-PROPOSAL.md`](../Proposals/JS-VOCABULARY-EXPANSION-PROPOSAL.md)
for the full catalog this ladder works through, and
[`docs/Implementation/JS-VOCABULARY-ADDENDUM-v0.070.md`](../Implementation/JS-VOCABULARY-ADDENDUM-v0.070.md)
stage 2 of 10 for the staging plan) -- the last of the genuinely
one-hour additions, plus the `Show` predicates that were already
speced but never wired up.

## What shipped

- `Derive.uppercase`, `Derive.trim` -- the missing string-casing
  siblings of `Derive.join`/`Derive.format`. Both are single-value
  transforms (same fixed arity as `Derive.count`): they read exactly
  one state/computed value, coerce it to a string (matching
  JavaScript's own `String(x)` coercion rather than throwing on a
  non-string value), and apply `.toUpperCase()`/`.trim()`.
- `Predicate.equals`, `Predicate.gt`, `Predicate.lt` -- `Show(...)`
  comparison predicates, already speced alongside `Derive.compare`'s
  `eq/ne/gt/lt/gte/lte` op set but never wired into
  `PREDICATE_REGISTRY` (which previously only had `truthy`/`falsy`).
  Each is its own fixed-arity `kind` (two names, mirrors `truthy`/
  `falsy`'s shape) rather than one `compare`-style kind plus an `op`
  extra arg -- `PredicateSpec` has no `extra_args` slot to carry one,
  and a closed predicate-per-comparison keeps `Show(...)`'s call
  sites reading the same way `Predicate.truthy(...)`/`.falsy(...)`
  already do.

```python
Computed("shout", deps=("name",), derive=Derive.uppercase("name"))
Computed("clean_input", deps=("raw",), derive=Derive.trim("raw"))

Show(Predicate.equals("role", "admin_role"), Text("Welcome, admin"))
Show(Predicate.gt("score", "threshold"), Text("You passed!"))
Show(Predicate.lt("stock", "reorder_point"), Text("Low stock"))
```

No changes to `arklight/ir/validate.py`'s validation *logic* for
either half of this stage (the existing `DerivationSpec`/
`PredicateSpec`-driven arity checks already cover the new registry
entries -- just an updated error message listing the new predicate
kinds) or to `arklight/ir/normalize.py`.

## Implementation

- `arklight/backend/js/derivations/uppercase.py`, `trim.py` (new) --
  each exports `NAME` + `JS_FRAGMENT`, mirroring `count.py`'s
  single-name shape. `arklight/backend/js/derivations/__init__.py` --
  registers both into `DERIVATION_MODULES`/`DERIVATION_FRAGMENTS`.
- `arklight/ir/schema.py` -- two new `DERIVATION_REGISTRY` entries
  (`uppercase`/`trim`: `min_names=1, max_names=1`) and three new
  `PREDICATE_REGISTRY` entries (`equals`/`gt`/`lt`: `names=2`).
- `arklight/ir/build.py` -- `_evaluate_derivation` gains `"uppercase"`/
  `"trim"` branches (Python `str.upper()`/`str.strip()`), kind-for-
  kind mirrors of the new JS fragments.
- `arklight/backend/html/page_render.py` -- `_evaluate_predicate`
  gains `"equals"`/`"gt"`/`"lt"` branches, the build-time twin of the
  client-side runtime change below.
- `arklight/backend/js/runtime/show.py` -- `arkEvalPredicate` gains
  the same three comparison cases, so a page's initial server-rendered
  `hidden` state and every subsequent client-side re-evaluation agree.
- `arklight/api.py` -- `Derive.uppercase`/`.trim` and
  `Predicate.equals`/`.gt`/`.lt` static methods, same shape as the
  existing `Derive.*`/`Predicate.*` methods.

## Tests

`tests/test_js_vocabulary_v0062.py` (new) -- API return values;
`PREDICATE_REGISTRY` coverage; validation (comparison predicates
reject anything but exactly two names); IR-build initial-value
evaluation for `uppercase`/`trim` (including non-string coercion);
HTML backend `Bind(...)` pre-fill and `Show(...)` `hidden` attribute
against `gt`/`equals` predicates; JS backend ships only the
derivation kind(s) actually used and includes all three new
`arkEvalPredicate` cases whenever `Show(...)` is used;
`DERIVATION_FRAGMENTS` registry coverage; and Node.js end-to-end
checks that the shipped `uppercase` fragment and the shipped
`arkEvalPredicate` `gt` case agree with their Python build-time
counterparts. Full suite: 1170 passed, no regressions.
