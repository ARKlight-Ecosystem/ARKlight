# v0.070 -- JS vocabulary: capstone (pluralize + random_int)

**Status: PLANNED -- not yet started.** Forward-looking summary,
written ahead of implementation as part of staging
[`docs/Implementation/JS-VOCABULARY-ADDENDUM-v0.070.md`](../Implementation/JS-VOCABULARY-ADDENDUM-v0.070.md)
(stage 10 of 10, the ladder's namesake). Will be updated to reflect
actual shipped behavior once this stage lands.

Tenth and final rung -- the two entries flagged throughout this
ladder as needing an explicit design exception before they ship,
placed last so review attention concentrates on them rather than
being spread across the whole catalog.

## What's planned

- **`pluralize`** -- `"item"` + count -> `"item"`/`"items"`,
  ubiquitous in list-count UI copy. English pluralization has enough
  irregular forms (`person` -> `people`, `octopus` -> `octopi`) that
  this ships with a small irregular-noun table plus a documented
  regular-plural-only fallback (`+s`/`+es`), not a claim of
  exhaustive coverage.
- **`random_int`** -- unlike every other derivation added across
  `v0.061`-`v0.069`, this is not a pure function of its inputs, which
  cuts against the "server-rendered `Bind` text agrees with the
  client recompute" invariant `sum.py`'s own docstring calls out.
  Ships with an explicit, documented exception: excluded from
  build-time pre-rendering entirely, resolved client-side only.

This closes the JS vocabulary addendum -- everything philosophy-
compliant from
[`docs/Proposals/JS-VOCABULARY-EXPANSION-PROPOSAL.md`](../Proposals/JS-VOCABULARY-EXPANSION-PROPOSAL.md)'s

The proposal's Tier 3 (client-side data fetch, reorderable lists,
sort/filter, file-upload preview) and Tier 4 (out of scope) remain
open, unaccepted proposals -- neither needs "more vocabulary," each
needs a new IR node or a philosophy exception this addendum
deliberately doesn't grant.
