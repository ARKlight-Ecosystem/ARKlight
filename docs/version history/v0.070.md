## `Provider`, stage 6 of 6 (capstone): capability vocabulary finalized (SHIPPED)

Closes the six-rung `Provider` ladder that opened at `v0.065`. Resolves
the accepted proposal's own open question §7.2 -- whether `capabilities`
would stay free-form or become a closed, finalized set -- placed last
on purpose so it's decided from five stages of real usage (IR
threading, JS emission, script loading, `arklight search`) instead of
guessed at stage 1. None of that usage ever needed a fifth well-known
name, so `PROVIDER_CAPABILITIES` (`auth`, `read`, `write`, `subscribe`)
is locked in as-is; the word "provisional" is retired from
`arklight/provider.py`, `arklight/ir/validate.py` and
`arklight/experimental.py`.

Finalizing the *known* four doesn't mean closing the vocabulary
outright -- a `Provider` exists so a site can point at *any* external
service, the same way a user-defined component covers markup ARKlight
has no built-in name for. So this stage also opens a namespaced escape
hatch:

- **`CUSTOM_CAPABILITY_PREFIX = "custom:"`** --
  `Provider.declare(capabilities=["auth", "custom:inventory-sync"])`
  names a capability the four well-known ones don't cover, without
  touching `PROVIDER_CAPABILITIES` or waiting on a new ARKlight
  release. Researched against two existing precedents before landing
  on this shape: the Language Server Protocol's `experimental`/
  vendor-namespaced capability keys, and OAuth's `custom:`-prefixed
  scope convention (both: closed core, explicit separate namespace for
  anything added on top).
- **Typo discipline unchanged** -- an unprefixed name is still checked
  strictly against the closed four (`"raed"` still fails as unknown,
  not accepted as a new custom word); only a name that opts in with
  the prefix gets the open treatment.
- **Custom labels are format-checked**, not merely non-empty:
  lowercase, starting with a letter, `-`/`_` allowed mid-label, no
  doubled or trailing separators -- `custom:`, `custom:Auth`,
  `custom:-x` still error. Reusing a well-known name under the prefix
  (`custom:read`) gets its own error pointing at the unprefixed form.
- `arklight search <name>` now tags each capability as it's declared --
  a bare name is one of the four, a `custom:`-prefixed one is this
  site's own.

This is the ladder's capstone: with stage 6 shipped, `Provider`'s own
six-stage implementation is complete, and its accepted proposal plus
implementation addendum have been retired from `docs/Proposals/`/
`docs/Implementation/` and graduated into the settled design record
[`docs/Foundational/PROVIDER-SDK.md`](../Foundational/PROVIDER-SDK.md)
-- see that file for the full contract, the finalized vocabulary, and
everything explicitly out of scope. `Provider` itself remains an
experimental feature (`provider-integration`/`provider-scripts` in
`arklight/experimental.py`) -- shipping the ladder doesn't graduate the
*feature* out of the experimental gate, only the *design* out of
"staged, in-flight."

`tests/test_provider.py` (82 tests) and the new, dedicated
`tests/test_provider_custom_capability.py` (45 tests) cover the
finalized vocabulary and the `custom:` path; full suite passing, no
regressions.

## JS vocabulary, stage 10 of 10 (capstone) -- PLANNED

Not yet started. Tenth and final rung of the JS vocabulary expansion
ladder -- `pluralize` (ships with a small irregular-noun table plus a
documented regular-plural-only fallback) and `random_int` (ships with
an explicit, documented exception: excluded from build-time
pre-rendering entirely, resolved client-side only, since unlike every
other derivation in the catalog it is not a pure function of its
inputs). See
[`docs/Implementation/JS-VOCABULARY-ADDENDUM-v0.070.md`](../Implementation/JS-VOCABULARY-ADDENDUM-v0.070.md)
for the full design.
