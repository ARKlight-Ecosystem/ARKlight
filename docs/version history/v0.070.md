## JS vocabulary, stage 10 of 10 (capstone): `pluralize` + `random_int`

Tenth and final rung of the JS vocabulary expansion ladder. Both
entries needed an explicit design exception before they could ship as
written -- see the addendum's "Scope filter" section -- and were
placed last in the ladder for exactly that reason, not because they
were large.

### What shipped

- **`Derive.pluralize(word, count)`** -- reads an ordered pair of
  state/computed names: a word and a count. `count == 1` returns the
  word unchanged; every other count pluralizes it. Ships with a small
  irregular-noun table (`person` -> `people`, `child` -> `children`,
  `octopus` -> `octopi`, `leaf` -> `leaves`, and 23 more) plus a
  documented regular-plural-only fallback (ending `s`/`x`/`z`/`ch`/`sh`
  -> `+es`; a consonant then `y` -> `ies`; otherwise `+s`) -- not a
  claim of exhaustive English pluralization. Lookup against the
  irregular table is an exact, case-sensitive string match, same as
  the shipped JS fragment's own plain object lookup: `"Person"` falls
  through to the regular rule rather than matching `"person"`.
- **`Derive.random_int(min=..., max=...)`** -- a whole number chosen
  uniformly at random from `[min, max]` inclusive
  (`Math.random()` composed with rounding). The one `kind` in the
  whole catalog that reads no state/computed names at all: the owning
  `Computed(...)`'s own `deps=(...)` (still required non-empty, like
  every `Computed(...)`) names whatever state should trigger a
  re-roll, entirely independent of what the derivation itself reads.
  `min` must not be above `max` (checked at build time, same rule
  `saturating_add`/`saturating_subtract` already use).

  **Documented design exception:** unlike every other derivation in
  the catalog, `random_int` is not a pure function of its inputs, so
  it can't honor the "server-rendered `Bind(...)` text agrees with the
  client recompute" invariant the rest of the catalog holds. It is
  therefore excluded from build-time pre-rendering entirely --
  `arklight.ir.build`'s `_evaluate_derivation` pre-fills `min` as a
  deterministic placeholder rather than attempting to reproduce
  `Math.random()` -- and always resolves client-side only. In
  practice a visitor with JavaScript enabled never actually sees the
  placeholder: `recomputeAll()` (`arklight/backend/js/runtime/
  state.py`) already re-derives every `Computed(...)` at construction,
  before the first paint, so the real roll lands immediately.

Both are pure registry-fragment additions -- one new file
(`arklight/backend/js/derivations/pluralize.py` /
`random_int.py`) plus one line each in `DERIVATION_REGISTRY`, same
shape every earlier rung of this ladder used. `arklight/ir/
js_string.py` gained `js_pluralize` as the build-time mirror for
`pluralize`; `random_int` needs no numeric mirror of its own, since
its build-time case is the documented placeholder above, not a
reproduction of the client's math.

`tests/test_js_vocabulary_v0070.py` (31 tests, including a Node parity
sweep for `pluralize` and an in-bounds/non-degenerate check for
`random_int`'s shipped JavaScript); full suite passing, no
regressions. With this stage shipped, the JS vocabulary addendum's own
ten-stage ladder is complete --
[`docs/Implementation/JS-VOCABULARY-ADDENDUM-v0.070.md`](../Implementation/JS-VOCABULARY-ADDENDUM-v0.070.md)'s
status table now reads SHIPPED end to end.

## `Provider`, stage 6 of 6 (capstone): capability vocabulary finalized (SHIPPED)

Closes the six-rung `Provider` ladder that opened at `v0.065`. Resolves
the accepted proposal's own open question §7.2 -- whether `capabilities`
would stay free-form or become a closed, finalized set -- placed last
on purpose so it's decided from five stages of real usage (IR
threading, JS emission, script loading, `arklight search`) instead of
guessed at stage 1. None of that usage ever needed a fifth well-known
name, so `PROVIDER_CAPABILITIES` (`auth`, `read`, `write`, `subscribe`)
is locked in as-is; the word "provisional" is retired from
`arklight/provider.py`, `arklight/ir/validate.py` and
`arklight/experimental.py`.

Finalizing the *known* four doesn't mean closing the vocabulary
outright -- a `Provider` exists so a site can point at *any* external
service, the same way a user-defined component covers markup ARKlight
has no built-in name for. So this stage also opens a namespaced escape
hatch:

- **`CUSTOM_CAPABILITY_PREFIX = "custom:"`** --
  `Provider.declare(capabilities=["auth", "custom:inventory-sync"])`
  names a capability the four well-known ones don't cover, without
  touching `PROVIDER_CAPABILITIES` or waiting on a new ARKlight
  release. Researched against two existing precedents before landing
  on this shape: the Language Server Protocol's `experimental`/
  vendor-namespaced capability keys, and OAuth's `custom:`-prefixed
  scope convention (both: closed core, explicit separate namespace for
  anything added on top).
- **Typo discipline unchanged** -- an unprefixed name is still checked
  strictly against the closed four (`"raed"` still fails as unknown,
  not accepted as a new custom word); only a name that opts in with
  the prefix gets the open treatment.
- **Custom labels are format-checked**, not merely non-empty:
  lowercase, starting with a letter, `-`/`_` allowed mid-label, no
  doubled or trailing separators -- `custom:`, `custom:Auth`,
  `custom:-x` still error. Reusing a well-known name under the prefix
  (`custom:read`) gets its own error pointing at the unprefixed form.
- `arklight search <n>` now tags each capability as it's declared --
  a bare name is one of the four, a `custom:`-prefixed one is this
  site's own.

This is the ladder's capstone: with stage 6 shipped, `Provider`'s own
six-stage implementation is complete, and its accepted proposal plus
implementation addendum have been retired from `docs/Proposals/`/
`docs/Implementation/` and graduated into the settled design record
[`docs/Foundational/PROVIDER-SDK.md`](../Foundational/PROVIDER-SDK.md)
-- see that file for the full contract, the finalized vocabulary, and
everything explicitly out of scope. `Provider` itself remains an
experimental feature (`provider-integration`/`provider-scripts` in
`arklight/experimental.py`) -- shipping the ladder doesn't graduate the
*feature* out of the experimental gate, only the *design* out of
"staged, in-flight."

`tests/test_provider.py` (82 tests) and the dedicated
`tests/test_provider_custom_capability.py` (45 tests) cover the
finalized vocabulary and the `custom:` path; full suite passing, no
regressions.
