# v0.042 -- Extra CSS features + CLI discoverability

Two smaller initiatives that were originally raised alongside the
`@media`/`<head>` request (what became v0.048) but scoped out of it
as a distinct problem: cutting boilerplate in capability that already
sort of existed, plus closing two CLI-discoverability gaps.

## What shipped

- **`Site.style(name, rules)`** -- custom CSS class authoring
  (`arklight/api.py`). `name` must be a valid single CSS class
  identifier (validated by regex); `rules` is a
  `{css-property: value}` dict, the same shape as the existing
  per-node `style={...}` prop, keeping the "no arbitrary CSS/HTML
  strings" boundary intact. Calling it again with a name already
  registered overwrites the previous definition (last call wins).
  Rendered by `CSSBackend.render()` as real `.name { prop: value; }`
  blocks, sorted by class and property name for deterministic
  output, appended after the base stylesheet so custom classes can
  override base rules purely by cascade order.
- **`arklight search <name>`** -- read-only component-schema lookup
  (`arklight/cli/search.py`), wired into `arklight/cli/main.py`.
  Case-insensitive exact match prints required props, whether
  children are allowed, and whether the component is a
  `Bind(...)`-able target. No exact match falls back to
  typo-tolerant "did you mean" suggestions (up to 5), implemented
  stdlib-only.
- **`arklight --help` / bare `arklight`** -- running `arklight` with
  no subcommand now prints the same help text `--help` would,
  instead of a terse argparse error.

Not part of this pass: `@keyframes`/`@font-face` (deferred to
v0.048), and searching utility/custom class names alongside
component schema in `arklight search`.
