## JS vocabulary, stage 5 of 10

Fifth rung -- the bulk of JS's own `String.prototype`, beyond the
casing helper from `v0.062`. `replace_first`/`replace_all` ship with
a hard requirement, not a suggestion: a literal substring argument
only, never a regex pattern string passed through `new RegExp(...)`.

### What's planned

- `capitalize`, `title_case`, `trim_start`, `trim_end`, `pad_start`,
  `pad_end`, `repeat`, `slice_string`, `char_at`, `replace_first`,
  `replace_all`, `split_count`, `reverse_string`, `string_length`,
  `includes_substring`, `starts_with`, `ends_with`, `is_empty`

## `Provider`, stage 1 of 6: the contract itself

The barebones interface a site can use to declare it talks to an
external service at runtime (Firebase was the motivating example, but
the contract is vendor-neutral) -- an interface only, no vendor code,
no networking code, shipped in ARKlight's core. Gated as an
experimental feature from the start, the same way `css-media-queries`
or `raw-postprocess` are.

### What's planned

- `Provider.declare(name=..., capabilities=[...])`, with `capabilities`
  validated against a closed vocabulary (finalized in stage 6).
- A new `provider-integration` entry in `arklight/experimental.py`'s
  `FEATURES` dict, following the existing three-step registration
  process.

## Rei, the compiler narrator (SHIPPED)

An opt-in `--narrate` flag on `arklight build`, sibling to the
existing `--verbose`/`--debug`: instead of `[ARKlight] ...` stage
lines, prints the same pipeline progress as short natural-language
sentences. A new `rei` section in `arklight.config.py` lets a project
pin its own default log mode (`plain`/`verbose`/`narrate`) instead of
passing a flag on every build. Pure Python, deterministic, no JSON,
no network, no LLM -- see
[`docs/Proposals/REI-COMPILER-NARRATOR-PROPOSAL.md`](../Proposals/REI-COMPILER-NARRATOR-PROPOSAL.md)
for the full design and
[`docs/Implementation/REI-COMPILER-NARRATOR-ADDENDUM.md`](../Implementation/REI-COMPILER-NARRATOR-ADDENDUM.md)
for the implementation plan.

### What shipped

- `--narrate` on `arklight build` (`arklight/cli/main.py`), mutually
  exclusive with `--verbose`/`--debug`: combining them fails the build
  up front, naming the conflicting flag. `--debug` still implies
  `--verbose` and is unaffected.
- `arklight/compiler/rei/` -- the renderer. It adds a second renderer
  over the same `on_stage=` callback `--verbose` already prints from
  (no new compiler hooks): a closed table of `re.fullmatch` patterns,
  one per stage message the pipeline emits, each mapped to a fixed
  sentence. Anything unrecognized falls back to a plain `[Rei] <message>`
  passthrough rather than being dropped. Stdlib only, deterministic.
  Inline experimental-API banners still print unconditionally and are
  never reworded.
- `rei.default_mode` config key (`"plain"`/`"verbose"`/`"narrate"`;
  `rei` added to `arklight/config.py`'s `_KNOWN_SECTIONS`). Only decides
  what a build with no log-mode flag does; a flag always wins. A missing
  section or key means `"plain"`; an unrecognized value fails the build.
- One-time introduction banner (Rei's greeting + which of `--narrate` /
  `arklight.config.py` turned narration on) on the first narrated build
  into a missing-or-empty output directory; not repeated on later builds
  into the same directory, and back again if the directory is cleared.
- `arklight search <name>` pointer on a schema violation:
  `ValidationError` gained a structured `component_name` field, set
  only at the SCHEMA-lookup sites in `arklight/ir/validate.py` (unknown
  component type, and missing required prop -- including their two
  `Repeat(...)`-template twins). The CLI reads it off
  `CompileError.__cause__` and Rei appends exactly one fixed
  `Try: arklight search <Name>` line; it is never derived by scraping the
  message text, and no other validation failure category gets a pointer.
- `docs/reference/eliza/eliza.py` -- vendored, read-only ELIZA reference
  copy. Nothing under `arklight/` imports it (enforced by a test that
  walks every module's real import statements).
- `docs/Foundational/CLI-REFERENCE.md` documents `--narrate` and
  `rei.default_mode`.
- `tests/test_rei_narrator.py` (31 tests, all passing; full suite 1810
  passed, 2 pre-existing/unrelated `test_version.py` failures from a
  bare non-`pip install`ed checkout, same as noted for Platform API IR
  below).

### Decision: narration on an import-time failure

The addendum and the proposal's §5 originally said a
`DuplicateComponentError`/`DuplicateStyleNameError` raised while the site
file runs would produce zero Rei output and surface as a raw Python
traceback. Building Rei showed that premise was wrong: the pipeline logs
"Discovering site..." *before* it executes the site file, and
`arklight.parser.loader.load_site` wraps any exception raised while
executing that file into `SiteLoadError` -> `CompileError`. These are
ordinary build errors in every log mode, never tracebacks.

Resolved by amending the spec to match, not by changing the pipeline
(deferring the stage line, or special-casing the loader, would also have
changed `--verbose` output). Under `--narrate` such a build prints the
discovery-stage line (and, on a fresh output directory, the one-time
introduction), then `[Rei] Compilation halted.` and the error text -- no
`arklight search` pointer, since there is no `component_name`. Under
`--verbose` it prints only the `[ARKlight] Discovering...` line before
the error. Pinned by six tests in `tests/test_rei_narrator.py`. The
proposal's §5 and the addendum's scope note and test bullet were
corrected accordingly.

## Platform API IR, stage 1 of 2: Web reference implementation (SHIPPED)

`PlatformAPI.notify(title, body=None)` and
`PlatformAPI.clipboard_write(text)` (`arklight.api.PlatformAPI`), used
on `on_click=` alongside named behaviors and `Action.*(...)`:

```python
Button("Notify me", on_click=PlatformAPI.notify("Saved!", body="Your changes were saved."))
Button("Copy link", on_click=PlatformAPI.clipboard_write("https://example.com"))
```

A compiler-owned interface registry (`arklight.ir.platform_api`)
describes each capability's arguments and required permissions,
independent of any backend; the Web backend supplies the actual
JavaScript (`arklight/backend/js/platform_apis/`), dispatched through
the same click interceptor `Action.*(...)`/named behaviors already
use, via a new `"platform:"` branch. A site that references no
Platform API ships none of this runtime, same "only ship what's used"
discipline as every other closed-vocabulary dispatch object. Building
against a backend that doesn't implement a referenced capability (any
backend other than Web, today) fails the build with a named-capability
diagnostic rather than silently dropping the request.

See
[`docs/Foundational/PLATFORM-APIS.md`](../Foundational/PLATFORM-APIS.md)
for the settled design record -- including the explicit boundary
between `PlatformAPI.clipboard_write` and the pre-existing `copy`
named behavior, both of which end up calling the same browser
clipboard API for different authoring needs -- and
[`docs/Implementation/PLATFORM-API-IR-ADDENDUM.md`](../Implementation/PLATFORM-API-IR-ADDENDUM.md)
for what Stage 2 (Android/Desktop native implementations) still needs.

### What shipped

- `arklight.ir.platform_api`: `PlatformAPISpec`,
  `PLATFORM_API_REGISTRY` (`notify`, `clipboard_write`),
  `BACKEND_PLATFORM_API_SUPPORT`, `PlatformAPIError`,
  `check_backend_support()`.
- `PlatformAPIRef` (`arklight.ast.nodes`), `PlatformAPI.notify`/
  `.clipboard_write` (`arklight.api`).
- Validation (`_validate_platform_api` in `arklight.ir.validate`):
  unknown-capability and unexpected-keyword-argument diagnostics.
- HTML compilation: `data-ark-on-click="platform:<capability>"` +
  `data-ark-platform-api-args` (`arklight.backend.html.attrs`).
- Web JS implementation for both starter capabilities
  (`arklight/backend/js/platform_apis/notify.py`,
  `clipboard_write.py`), a `"platform:"` click-dispatch branch
  (`arklight/backend/js/runtime/dispatch.py`), and full runtime
  assembly wiring -- usage collection, the `platformApis` dispatch
  object, and the backend-support check actually running during a
  build (`arklight/backend/js/render.py`).
- `tests/test_platform_api.py` (18 tests, all passing; full suite
  1313 passed, 2 pre-existing/unrelated `test_version.py` failures
  from a bare non-`pip install`ed checkout).
