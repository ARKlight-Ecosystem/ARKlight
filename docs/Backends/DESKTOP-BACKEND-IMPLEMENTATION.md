# Desktop Backend Implementation: Staged Order

Status: **Stages 1-4 done** (Linux only), Stages 5-7 not started. This
file plays the same role for the desktop backend that
`ANDROID-BACKEND-IMPLEMENTATION.md` plays for the Android one: it
doesn't restate the architecture already decided in
`ARKLIGHT_DESKTOP_BACKEND_PROPOSAL.md` (native host, in-memory asset
store, `ark:` resource scheme, zero custom JS API), it exists to turn
that proposal into a trackable table, mirroring the Android backend's
own CI-first-then-local staging shape (Stages 2-4 are CI-only, no
local toolchain required; Stages 5-7 are their `subprocess`-shelling-
out local counterparts).

`NEUTRALINO-INTEGRATION.md` describes an earlier, superseded plan
(Neutralino.js as the canonical desktop backend) -- see the proposal's
section 11 for why that direction was dropped. Nothing in this table
depends on it.

## Platform scope

**Linux only for now.** The proposal's architecture (native host +
platform WebView + in-process resource scheme) is platform-neutral by
design, but Stage 1 below only implements the Linux host: GTK3 +
WebKit2GTK, the WebView every mainstream Linux desktop already has
available via distro packages. Windows (WebView2) and macOS
(WKWebView) hosts are later, not-yet-started work -- see "Explicitly
out of scope" below. `arklight desktop scaffold --target linux` is
explicit (not just an implied default) precisely so a future
`--target windows`/`--target macos` is additive, not a breaking
rename.

Each rung is independently useful and additive, same
"`arklight pack` runs after `build`, never touching the compiler
internals" shape `arklight.packer` already established, and the same
"CI-only stages ship before their local-toolchain counterparts"
ordering the Android backend's own table uses -- `arklight desktop`
reads an existing `build-dir` and never imports the parser/ir/HTML/
CSS/JS backend internals it's packaging.

## App identity metadata

`arklight.config.py`'s `"desktop"` section, read by
`arklight.cli.desktop.scaffold_project` (mirrors `arklight.cli.
android`'s own `"android"` section):

```python
CONFIG = {
    "desktop": {
        "app_name": "My Site",          # str, default "ARKlight App"
        "app_id": "com.example.mysite", # dotted reverse-DNS id, default "com.arklight.app"
        "window_title": None,           # str or None; None -> falls back to app_name
        "width": 1024,                  # positive int, default 1024
        "height": 768,                  # positive int, default 768
        "resizable": True,              # bool, default True
    },
}
```

`app_id` is the same dotted, reverse-DNS-style identifier shape the
Android backend's `package_id` already uses (not a Python/Java
package here -- just a stable, namespaced identifier), reused as the
generated `.desktop` launcher entry's filename and the window's
program name (`g_set_prgname`, which GTK derives `WM_CLASS` from). No
`icon`/`splash` keys yet -- see "Explicitly out of scope" below.

## Stage 1 implementation notes

Decisions made while landing `arklight.cli.desktop`/
`arklight.backend.desktop.runtime` that weren't already pinned down by
the proposal:

- **Unpacked tree, not a `.ark` bundle, is what gets embedded.** The
  proposal's section 5 describes the `.ark` bundle as the eventual
  application payload, but parsing its zip/sealing format from C is a
  real dependency (a zip library at minimum, a crypto one for sealed
  bundles) this first Linux target doesn't need to take on yet. Same
  call the Android backend's Stage 1 made for the same reason (see
  ANDROID-BACKEND-IMPLEMENTATION.md's "Open questions for Stage 0" --
  "an unpacked tree skips `ArkBundle`/`ArkSeal` entirely for the
  common case"). Packing a real `.ark` bundle as the embedded payload
  is future work, not ruled out, just not Stage 1's problem.
- **Byte arrays, not a linker trick.** `assets.gen.c` embeds each
  file's bytes as a plain C array literal rather than `ld -r -b
  binary`/`objcopy`/C23's `#embed` -- portable across whatever C
  toolchain the user's distro ships, at the cost of a large generated
  source file for a big site. Acceptable for a first target; revisit
  if that ever becomes the actual bottleneck a real site hits.
- **`ark:///path` (empty authority), not `ark://site/path`.** Simpler
  to resolve from `webkit_uri_scheme_request_get_path()` without
  reasoning about the scheme's authority component, and ARKlight's
  HTML backend already emits page-relative links, so relative
  resolution against `ark:///index.html` lands on `ark:///about.html`,
  `ark:///assets/logo.svg`, etc. with no rewriting needed on this
  side.
- **Zero custom native JavaScript API**, per the proposal's section
  10 -- the generated page's JS runs directly in WebKit2GTK's own
  engine, nothing crosses into `main.c`.
- **Navigation policy**: anything not on the `ark:` scheme (http(s),
  mailto, ...) is handed to `g_app_info_launch_default_for_uri` (the
  user's default external handler) and blocked from navigating the
  app's own window there, per the proposal's section 9.
- **`-o`/`--output` is required** (unlike `arklight new`), same
  reasoning `arklight android scaffold` already gives: a scaffolded
  desktop project sitting anonymously in an already-multi-purpose
  project directory is more likely to be a mistake than a plain site
  scaffold is.
- **`--target` is explicit and validated even though only one value
  exists yet** (`SUPPORTED_TARGETS = ("linux",)` in
  `arklight.cli.desktop`) -- adding Windows/macOS later only means
  extending that tuple plus whichever platform-specific runtime module
  backs it, not renaming an implicit default out from under existing
  scripts.

## Stage 2 implementation notes

Decisions made while landing the generated CI workflow that weren't
already pinned down by Stage 1's own notes above:

- **One job, not two.** The Android backend's workflow splits
  `assemble-debug` and `install-launch-smoke-test` into separate jobs
  (the second `needs:` the first, downloading its APK as an
  artifact). Stage 2 here is only the build half of that split --
  there's no second job yet because there's no smoke-test logic yet
  to put in it (that's Stage 3). Splitting the single `build` job
  into two now, ahead of Stage 3 actually needing the second one,
  would just be a job that re-downloads its own binary for no reason.
- **`project_subdir` mirrors the Android backend's parameter of the
  same name, byte-for-byte the same reasoning.** Including
  `_find_enclosing_git_root` itself: kept as its own copy in
  `arklight.cli.desktop` rather than a shared import, same "each
  backend's `cli` module is otherwise self-contained" shape
  `arklight.cli.android`/`arklight.cli.scaffold` already have.
- **No `arklight desktop scaffold` flag to opt out of generating the
  workflow.** Unlike the Android backend's `--release` (genuinely
  a no-op without secrets the tool has no business assuming exist),
  a plain build-and-upload job has no equivalent "does nothing useful
  by default" failure mode -- it works unconditionally the moment
  it's generated, same as the Android backend's own `assemble-debug`
  job. It's a normal, hand-editable/hand-deletable file like every
  other generated file here, not a config toggle.

## Stage 3 implementation notes

Decisions made while landing the launch smoke-test job that weren't
already pinned down by Stages 1-2's own notes above:

- **`xvfb-run`, not a manual `Xvfb & export DISPLAY=...` dance.**
  `xvfb-run --auto-servernum bash .github/scripts/desktop-smoke-test.sh`
  starts a throwaway X server, sets `$DISPLAY` for the wrapped
  command, and tears the server down again on exit -- one line, no
  separate "start Xvfb in the background, wait for it to be ready,
  remember to kill it" steps for this workflow to get right itself.
- **Search for the binary by name (`find bin -name '<binary>'`),
  don't assume a fixed downloaded path.** Same reasoning the Android
  backend's own `_android_smoke_test_sh` gives for its `find apk -name
  '*.apk'` -- `actions/download-artifact` doesn't guarantee it
  preserves the `path_prefix` a nested-project's upload step used
  (a single-file `path:` upload is stored flat in the artifact
  regardless), so `_desktop_smoke_test_sh` doesn't assume one either.
  This also means the smoke-test job needs no `project_subdir`
  handling of its own, unlike `build`'s `make` step.
- **Background-launch + `kill -0` liveness check, not `adb shell
  pidof`.** There's no `adb` equivalent for a plain Linux binary --
  `_desktop_smoke_test_sh` backgrounds the process directly (`"$BIN"
  &`), waits 5 seconds (same window `_android_smoke_test_sh` waits
  before its own `pidof` check), and confirms the PID is still alive
  with `kill -0`. Cleans up with a final `kill`/`wait` on success so
  the job doesn't leave an orphaned GTK process behind on the runner.
- **Runtime libs, installed separately from the `build` job's `-dev`
  ones.** `libgtk-3-0`/`libwebkit2gtk-4.1-0` (no `-dev` suffix) are
  what's needed to *run* the binary, distinct from the headers/static
  libs `build`'s `libgtk-3-dev`/`libwebkit2gtk-4.1-dev` install to
  *compile* it -- installed in their own step in the
  `launch-smoke-test` job rather than reusing `build`'s package list,
  since the two jobs run on separate, independent runners with
  nothing installed between them.
- **Kept as a second job (`launch-smoke-test`), not folded into
  `build`.** Now that Stage 3 gives the single `build` job from Stage
  2 something to actually depend on it (`needs: build`, downloading
  its uploaded binary), this is the split Stage 2's own
  implementation notes above flagged as not-yet-worth-doing. Same
  "does this thing actually start and stay up" question the Android
  backend's own `install-launch-smoke-test` job asks of its `assemble-
  debug` job's APK.

## Stage 4 implementation notes

Decisions made while landing the `package` job that weren't already
pinned down by Stages 1-3's own notes above:

- **Tarball, not a `.deb`.** A real distro package is called out as a
  stretch goal in the table above, not this stage's requirement --
  `tar czf` needs nothing beyond what every other job here already
  has (no `dpkg-deb`, no `fpm`, no per-distro packaging tool to
  install), and a plain tarball is still strictly more distributable
  than the bare `bin/<binary>` artifact Stage 2 already uploads.
  A `.deb`/`.rpm`/etc. shape is `arklight desktop build --package`'s
  problem too (Stage 7), whenever it lands.
- **Depends on `build` alone, not `launch-smoke-test`.** Mirrors the
  Android backend's own `assemble-release` job, which independently
  rebuilds from source rather than waiting on its debug build's smoke
  test -- packaging a binary that hasn't been smoke-tested yet is a
  little unusual, but forcing every user who wants a downloadable
  artifact to also wait on the (slower, `Xvfb`-booting) smoke-test job
  first would be an odd coupling this table's own "Depends on: Stage
  2" column deliberately doesn't ask for. A user who cares can still
  just look at both jobs' status before trusting an artifact.
- **A second `actions/checkout@v4`, not passing the `.desktop` file
  through `upload-artifact` from `build`.** `build`'s own artifact is
  scoped to `bin/<binary>` alone (see Stage 2's own implementation
  notes -- `if-no-files-found: error` on a single glob), and widening
  it to also carry the `.desktop` file just to avoid a second, cheap
  checkout in an already-independent job would couple two artifacts'
  shapes together for no real savings. Every other job in this
  workflow already re-checks-out for its own reasons (`launch-smoke-
  test` does the same for `.github/scripts/desktop-smoke-test.sh`).
- **Staging directory named `<binary>-linux`, matching the tarball's
  own basename once extracted.** Same "the archive's top-level
  directory matches what you'd expect from the filename" convention
  most hand-built release tarballs already follow, so `tar xzf
  <binary>-linux.tar.gz` doesn't scatter two loose files into
  whatever directory the user happened to extract it in.
- **`find bin -maxdepth 1 -type f | head -n1`, not a name match.**
  Same reasoning `_desktop_smoke_test_sh` gives for its own `find bin
  -name '<binary>'` (`actions/download-artifact` doesn't guarantee it
  preserves upload-side path prefixes), except the package job's step
  doesn't even need the binary's exact name -- it renames it to
  `$STAGE/<binary>` explicitly in the same `cp`, so a bare "the one
  file in `bin/`" lookup is enough.

## Explicitly out of scope (for now)

Same spirit as the Android backend's own "Explicitly out of scope"
list -- repeated here so this table doesn't imply any of it is
Stage-1 work: Windows/macOS hosts, app/window icons (`desktop.icon` /
`desktop.splash` config keys don't exist yet -- deliberately, rather
than half-wired), a sealed `.ark` bundle as the embedded payload (see
"Stage 1 implementation notes" above), any native JavaScript bridge
beyond serving assets, an application updater, a distro-native
installer/package beyond Stage 4/7's plain artifact, and any change to
the HTML/CSS/JS backends themselves -- this is a packaging backend
that consumes an existing `build-dir` as opaque input, the same way
`arklight.packer` and the Android backend already do.
