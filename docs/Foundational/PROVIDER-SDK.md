# Provider

Settled design record for `Provider`, ARKlight's barebones, experimental
interface for a site to declare that it talks to an external service at
runtime (a hosted database, an auth service, a hand-rolled API). Accepted
from a proposal and staged as a six-rung implementation ladder,
`v0.065`-`v0.070`, one stage per version; all six stages are now SHIPPED
and the ladder is closed. This file records the decisions that don't
change; `PROGRESS.md`/`CHANGELOG.md` carry the per-stage shipping history
(`0.06514`, `0.06516`, `0.06518`, `0.06613`, `0.06614`, `0.06616`).

Both the original proposal and the six-rung addendum that staged it have
been retired from `docs/Proposals/`/`docs/Implementation/` now that every
stage has shipped, per that folder's own graduation rule -- this file is
what they graduated into. See `docs/version history/v0.065.md` through
`v0.070.md` for the shipped-behavior summary of each stage, and
`arklight/provider.py` for the implementation itself.

## What "barebones" means here, precisely

- **An interface only.** `Provider` is a fixed, closed shape a concrete
  implementation must satisfy -- structurally the same kind of thing
  `Backend` already is for output targets. `arklight/provider.py` holds
  no method that does anything by itself.
- **No shipped implementations.** ARKlight's core does not ship a
  Firebase provider, a Flask provider, or any other concrete
  integration. That remains the site author's own code (or a separate,
  non-core package written against the contract) -- never something
  this project maintains, tests against a live third-party service, or
  takes a support burden for.
- **No logic, no opinions.** The contract does not decide what auth
  looks like, what a database schema looks like, or how errors from the
  external service should be handled. It only defines *where* a site's
  declared capabilities plug in and *what shape* data crosses that
  boundary.
- **Zero cost when unused.** A site that never declares a `Provider`
  ships no `Provider` code at all -- pages and stylesheet stay
  byte-identical with and without one, the same "only ship what's used"
  discipline the JS backend already applies to `actions`/`behaviors`/
  `derivations`.

Named "Provider", not "backend", because `arklight/backend/` already
means *output target* (HTML, CSS, JS, Android, Desktop) -- a `Provider`
is a completely different concept, a site opting in to talking to an
external *service* at runtime.

## The contract

```python
from arklight import Provider, Site

site = Site(
    provider=Provider.declare(
        name="firebase",               # any label, not a fixed list of vendors
        capabilities=["auth", "read"],  # the finalized vocabulary, see below
    )
)
```

`Provider.declare(...)` returns an immutable, already-validated
`ProviderDeclaration`; `Site(provider=...)` attaches it. At compile time
ARKlight:

1. Validates the declared `capabilities` against the closed vocabulary
   (below) -- the same kind of schema check `arklight/ir/validate.py`
   already does for every other component and prop.
2. Threads the declaration through `WebsiteIR.provider`, re-validated at
   the pipeline's own validation stage (`validate_provider`) as defense
   in depth alongside `ProviderDeclaration.__post_init__`'s own
   construction-time check.
3. Emits one small, fixed, read-only config object in `arklight.js`:
   `window.ARKLIGHT_PROVIDER = Object.freeze({name, capabilities})`, for
   the site author's own script to read. Nothing else -- no network
   call, no vendor SDK, no generated glue that actually talks to
   anything. The concrete implementation (the real Firebase JS SDK,
   initialized with a project's real config, doing the real
   `auth.signIn(...)` call) is the site author's own code, not
   generated by ARKlight.
4. Makes the declaration discoverable: `arklight search <provider-name>`
   prints the declared contract (name, capabilities, and where the same
   data is visible at runtime), the same "look something up without
   opening a file" convenience components already get.

A declared `Provider` on its own carries no `<script src>` for the
vendor SDK it eventually talks to -- `Page(scripts=[{"src": "...", ...}])`
is the separate, separately-gated primitive that loads one (see
"External script loading" below).

## The finalized capability vocabulary

`PROVIDER_CAPABILITIES = ("auth", "read", "write", "subscribe")` --
the four the original proposal itself listed. Five stages of real usage
against the interface (IR threading, JS emission, script loading,
`arklight search`) never needed a fifth well-known name, so this set is
now **finalized**: nothing is added, renamed, or removed here again,
the same closed-registry discipline `Action.*`/`Behavior.*` already use
everywhere else in the runtime, and for the same reason -- it keeps
generated output inspectable and keeps ARKlight's "no eval, no
`new Function`, no string ever executed as code" promise intact even as
this surface grows.

Finalizing the *known* four doesn't mean closing the vocabulary
outright: a `Provider` exists so a site can point at *any* external
service, the same way a user-defined component covers markup ARKlight
has no built-in name for, so a hard four-name ceiling would cut against
that. A namespaced escape hatch opens it back up without reopening the
closed set:

- **`CUSTOM_CAPABILITY_PREFIX = "custom:"`.**
  `Provider.declare(capabilities=["auth", "custom:inventory-sync"])`
  names a capability the four well-known ones don't cover, without
  touching `PROVIDER_CAPABILITIES` or waiting on a new ARKlight release.
  Researched against two established precedents for extending a small
  closed protocol without renegotiating it: the Language Server
  Protocol's `experimental`/vendor-namespaced capability keys, and
  OAuth's `custom:`-prefixed scope convention (both: closed core,
  explicit separate namespace for anything added on top).
- **Typo discipline unchanged.** An unprefixed name is still checked
  strictly against the closed four -- `"raed"` still fails as an
  unknown capability, not silently accepted as a new custom word. Only
  a name that opts in with the prefix gets the open, SDK-flexible
  treatment.
- **Custom labels are format-checked**, not merely non-empty: lowercase,
  starting with a letter, `-`/`_` allowed mid-label
  (`custom:inventory-sync`), no doubled or trailing separators -- so
  `custom:`, `custom:Auth`, `custom:-x` all still error as unknown.
  Reusing a well-known name under the prefix (`custom:read`) gets its
  own dedicated error pointing at the unprefixed form, rather than
  silently accepting a confusingly-named duplicate.
- `arklight search <name>` tags each capability as it's declared -- a
  bare name is one of the four finalized well-known ones, a
  `custom:`-prefixed one is this site's own -- so a reader doesn't have
  to hold `PROVIDER_CAPABILITIES` in their head to tell which is which.

## External script loading

A `Provider` declaration alone doesn't get a real vendor SDK (the
actual Firebase JS SDK, say) loaded into the page -- that needs its own
authored escape hatch: `Page(scripts=[{"src": "https://.../sdk.js", ...}])`,
validated the same `{attribute: value}`-dict, `src`-required structural
discipline `Page(links=[...])` already uses, and rendered as verbatim
`<script ...></script>` tags at the end of `<head>`. A `"javascript:"`
`src` is rejected outright -- this loads an external file, it is not an
inline-code escape hatch.

Gated as its own `provider-scripts` experimental feature, separate from
`provider-integration`: loading an arbitrary external script is a
distinct risk from declaring a capability contract, so a page can carry
either without the other, and each records its own `ExperimentalUsage`.
An external script's origin also has to clear the page's own
`script-src 'self'` CSP default via `Site(trusted_script_origins=[...])`
(or `Site(strict_csp=False)`) -- unlike a bare `Provider` declaration,
this one is a real `script-src` concern, and the tag a build adds can
otherwise be blocked by the very policy the same build emits.

## Experimental gating

Two separate entries in `arklight/experimental.py`'s `FEATURES` dict,
both excluded from the heavy-reliance nudge (`upstream_candidate=False`)
-- a `Provider` is a deliberate architectural boundary, not a missing
feature ARKlight should eventually absorb:

- **`provider-integration`** -- fires when a page's IR shows a declared
  `Provider`. The service on the other end is entirely outside anything
  ARKlight can validate: ARKlight ships no vendor SDK, makes no network
  calls, has no opinion about auth, and does not implement, audit, or
  guarantee the service.
- **`provider-scripts`** -- fires when a page uses `Page(scripts=[...])`.
  Flagged for the same reason `css-import` is: the referenced file is
  fetched and run at request time, so its contents can't be validated
  by ARKlight the way everything else it generates is.

Printed both inline (at the point a page's IR shows the usage) and in
the end-of-build summary, the same two-surface contract every other
experimental feature gets. Not gated behind `--verbose` -- this is the
entire point of gating, not incidental extra output.

## Explicitly out of scope

- No bundled Firebase, Supabase, or any other vendor SDK, now or as a
  planned follow-up.
- No server ARKlight stands up, packages, or deploys on the site
  author's behalf -- ARKlight remains a compiler producing static
  files.
- No opinion on auth flows, token storage, or security rules -- that
  risk belongs entirely to whichever concrete `Provider` implementation
  a site chooses.
- No client-side data-fetch orchestration (loading states, caching,
  retries). That remains a separate, larger, still-open gap in the JS
  vocabulary catalog (`docs/Implementation/JS-VOCABULARY-ADDENDUM-v0.070.md`)
  -- `Provider` is meant to be the vendor-neutral boundary that feature
  would eventually plug into, not a rebuild of it here.
- No DOM hooks or `State(...)` keys wired to a capability -- there is
  no authoring surface for that yet; `window.ARKLIGHT_PROVIDER` only
  ever gains fields, it doesn't drive reactive state on its own.

## Why this doesn't violate "Compiler First"

`SYSTEM-DESIGN-AGREEMENTS.md`'s central rule is: *if the compiler can
solve it correctly and completely, the runtime shouldn't solve it
again.* A live network call to a third-party service is, definitionally,
not something the compiler can resolve ahead of time -- it depends on
data that doesn't exist until a real user, with a real session, hits a
real endpoint. That puts it in the same category
`SYSTEM-DESIGN-AGREEMENTS.md`'s "Runtime Is a Delegation Boundary"
section already carves out for network responses, local storage, user
input, and OS APIs. The compiler's job is limited to what it *can* still
own: validating the capability declaration, deciding which minimal
config to bake in, and deciding what (if anything) ships when the
feature isn't used.

## Relationship to `arklight/backend/`

`arklight/backend/{html,css,js,android,desktop}/` are *output targets*
-- what the compiler emits *to*. A `Provider` is a site *talking to*
something else entirely at runtime, after the build is done -- hence
the deliberately different name, chosen specifically to avoid that
collision.
